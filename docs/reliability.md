# Безопасные файлы и устойчивый эфир

Реализовано 2026-09-05. Используются стандартные Go API и уже подключённый SQLite;
новых зависимостей нет. Локальный анализ выбранного файла в браузере не менялся.

## Хранение и импорт

Каждая загрузка резервирует уникальный каталог
`music.dir/.radiopump/<32 hex символа>/`. Сервер пишет `.upload`, проверяет лимит
размера и сигнатуру, выполняет Sync/Close, затем переименовывает файл в готовый
`<безопасное-имя>.<расширение>`. Запись трека создаётся после публикации.
Одинаковые имена в конкурентных запросах не могут перезаписать друг друга.

JSON `POST /api/admin/tracks` сохраняет контракт полей, но меняет смысл `path`:
это источник **копирования**, существующий обычный файл внутри `music.dir`.
Поддерживаются абсолютные пути и прежние пути относительно рабочего каталога
сервера, например `music/source.flac`. Путь относительно самой музыкальной папки
не подставляется автоматически. URL, выход из корня, каталоги, устройства,
симлинки и пути через родительские симлинки отклоняются. Скопированное аудио
проходит те же лимиты/проверки, что multipart. Исходник остаётся на месте даже
после удаления импортированного трека. Неверный путь даёт `400`, превышение
размера — `413`; JSON body ограничен 64 KiB.

Файловые операции выполняются через `os.Root`. FFmpeg дополнительно проверяет
локальный путь и обычный тип файла, использует только протоколы `file,pipe`.
Проверка сигнатуры не гарантирует успешного декодирования: повреждённое аудио
обрабатывается как ошибка эфира.

`/music/*` раздаёт аудиофайлы через Root с поддержкой Range. Индекс каталогов,
временные upload и каталог восстановления не публикуются.

## Удаление и восстановление

Миграция №2 добавляет `pending_file_deletions`. Repository атомарно удаляет
трек/связи и записывает намерение удалить файл. Сервис удаляет файл, только если
больше нет ссылок на него. Для старых записей учитываются эквивалентные варианты
пути с `./`, разделителями и регистром Windows. Новый импорт всегда создаёт копию.

- `204 No Content`: удаление завершено либо файл ещё нужен другой записи.
- `202 Accepted`, `{"status":"file_deletion_pending"}`: запись удалена, но
  очистка файла ожидает повторной попытки. Админский веб показывает уведомление.
- `400`: опасный старый путь; файл и запись не удаляются.
- `404`: записи нет.

Отложенные задания повторяются при старте и каждые 30 секунд. Ошибки пишутся
в журнал. Отсутствующий файл считается уже удалённым. Отказ удаления при rollback
неудачной загрузки тоже записывается в очередь. Если недоступны и диск, и БД,
файл попадёт под startup recovery.

Recovery запускается до HTTP и worker-ов. Незавершённые `.upload` очищаются.
Готовые файлы из `.radiopump`, на которые нет ссылок БД или pending-удалений,
переносятся в `music.dir/.radiopump-recovery/<id>/`. Они **не уничтожаются**:
отсутствие записи может означать откат или утрату БД. Для восстановления можно
выполнить защищённый JSON-импорт такого файла; это создаст новую копию и запись.
Автоматического восстановления метаданных и отдельного UI пока нет.
Пользовательские файлы вне служебного namespace recovery не обходит.

Сервер удерживает SQLite EXCLUSIVE-транзакцию в отдельном
`music.dir/.radiopump-lock.db`. Второй процесс с той же библиотекой не запускается;
при падении процесса ОС освобождает блокировку. Блокировка не занимает `radio.db`.
Служебные каталоги нельзя использовать как ручную музыкальную папку. Резервная
копия должна сохранять вместе `data/radio.db` и весь `music.dir`.
Это восстановление после прерывания процесса, а не гарантия против повреждения
диска или потери питания; полноценный backup/restore остаётся отдельным этапом.

## Эфир и очереди

Каждая волна имеет собственный контекст отмены. `Station.Close` и
`PlaybackEngine.Close` повторяемы и ждут broadcaster/worker/FFmpeg. Реестр волн
защищён mutex, повторный ID запрещён. Входной канал не закрывается потребителем.
SIGINT/SIGTERM останавливают эфир, завершают HTTP, фоновые задачи и закрывают БД.
HTTP shutdown ограничен 15 секундами; после превышения соединения закрываются.

Пустая библиотека, исчезнувший или повреждённый файл не завершают worker.
После серии ошибок пауза растёт от 1 до 30 секунд; успешный трек сбрасывает её.
Все паузы отменяемы. Без подходящего аудио HTTP-соединение может ждать данные:
генератор тишины/fallback ещё не реализован. Добавленная музыка будет обнаружена
при следующей попытке. Выбор очереди отделён от реального состояния аудиоплеера.

Scheduler сериализует выбор отдельно для каждой волны. Инвалидизация увеличивает
поколение; SQL-снимок, полученный до нового изменения библиотеки, отбрасывается.
После трёх конфликтов worker повторит операцию с backoff. Пустая выборка очищает
старую очередь. При полном цикле избегается немедленный повтор текущего трека,
если есть альтернативы. Семантика фильтра тегов остаётся ИЛИ.

FFmpeg получает `-re`, явную первую аудиодорожку, единые bitrate/sample rate,
отключённые ID3/Xing и копирование исходных метаданных. Watchdog отменяет процесс
после 15 секунд без выходного аудио; stderr ограничен 16 KiB. Отмена действует
также при блокировке передачи в выходной канал. Новый процесс на каждый трек
сохраняется: бесшовность и выравнивание громкости пока не гарантируются.

## Слушатели и ресурсы

`stream.buffer_seconds` теперь задаёт приблизительную вместимость очереди будущих
CBR MP3-данных каждого слушателя. Значение по умолчанию 5, допустимо 1–30 секунд.
Это не кольцевая история: новый слушатель получает будущие чанки текущего эфира.
Чанк ограничен 4096 байт; вместимость округляется вверх до целого чанка.
Например, 128k и 5 секунд дают 20 чанков, до 81920 байт. Короткие финальные чанки
могут уменьшать фактическую временную вместимость.

На волну допускается до 256 подписчиков. При переполнении подписка завершается:
хвост очереди освобождается, новые байты этому клиенту больше не отправляются.
Здоровые подписчики продолжают получать поток. Каждая HTTP Write/Flush ограничена
10 секундами; глобальный WriteTimeout остаётся нулевым для длительного эфира.
После остановки движка и при превышении лимита новые подключения получают `503`
с `Retry-After: 5`. Неизвестная волна — `404`. `X-Accel-Buffering: no` отключает
буферизацию у поддерживающего этот заголовок reverse proxy.

## Проверки и ограничения

Регрессии покрывают конкурентные upload, внешние пути, recovery, retry удаления
и rollback, старые общие пути, эксклюзивного владельца библиотеки, пересечение
инвалидизации с чтением очереди, параллельный lifecycle, пустую станцию, отказ
decode, лимит подписчиков и deadline блокирующей записи.

Реальные FFmpeg-fixtures проверяют WAV/FLAC/MP3 → последовательный MP3 с повторным
декодированием, отмену процесса, а настоящий router/HTTP-сервер — несколько
слушателей, пять переподключений и остановку. Браузерные регрессии отдельно
покрывают все 29 прежних сценариев анализа форматов и обложек.

Windows-тест симлинков пропускается, если у процесса нет привилегии их создания.
`go test -race` требует CGO и C-компилятор, которых нет в текущем окружении.
Длительная нагрузка, настоящий медленный сетевой клиент и визуальный браузерный
UI не проверены; блокировка записи проверена управляемым ResponseWriter.
Публичный now-playing API и live-веб добавлены следующим этапом — [Страница радио](radio-page.md). WebSocket, gapless/crossfade,
нормализация громкости и production-авторизация не входят в этот этап.
